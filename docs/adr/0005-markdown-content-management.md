# 0005: Markdown を編集元とし、検証済みモジュールへ変換する

- 状態: Accepted
- 日付: 2026-10-30
- 置き換える判断: [0001](0001-typed-local-content.md)、[0004](0004-sourced-activity-periods.md) の保管方法。期間・出典の意味は継承する。

## 背景

VS Code を管理画面のように使い、実績を後から差し込みたい。配列の TypeScript を編集する方法では、説明文を書く作業とプログラムの編集が近すぎる。一件ずつファイルとして扱い、本文を Markdown で書けることを優先する。

## 決定

- 編集元を `content/` に集約し、制作物・活動・技術グループを一件一ファイルの `.md` にする。プロフィールと表示設定も Markdown で管理する。
- YAML front matter はメタデータ、本文は Markdown とする。`gray-matter` と YAML 1.2 core schema で解析し、Zod でフィールド、日付、期間、URL、ID の重複を検証する。
- 年・年月・年月日の精度と、継続中を表す `present` を維持する。出典 URL は各ファイルの `links` に残す。
- `draft: true` の本文と設定は公開データに含めない。下書きのメタデータも検証し、新規作成は下書きを初期値にする。
- 検証後に `src/content/generated.ts` を生成する。このファイルは Git 管理せず、Next.js の型チェックとモジュール監視を利用する。
- 開発スクリプトは Markdown の変更・追加・削除を監視する。入力ミスでは直前の有効な生成結果を保ち、ファイル名と項目を表示する。生成結果は一時ファイルからの置換で更新する。
- 本番ビルドの前に同じ変換を実行する。不正なデータがあればビルドを止める。描画時にはファイルシステムや外部 API を読まない。
- 本文は `react-markdown` と `remark-gfm` で描画する。Markdown 内の見出しは項目名より下位にし、表・チェックリスト・コードに対応する。HTML や MDX は実行しない。
- VS Code の Front Matter CMS に一覧・フィールドの設定を提供する。拡張がなくても Markdown・テンプレート・追加タスクで同じ操作ができる。
- サイドバーへは Server Component からデータを渡し、ブラウザ用コンポーネントから編集元・生成処理を参照しない。

## 検討した選択肢

- 描画時に `fs` で読む: 実装は簡単だが、開発時の新規ファイルへの追従とホットリロードを別途考える必要がある。
- MDX を実行する: 表現力は高いが、内容の追加に JavaScript の知識が必要になり、本文がコードになる。
- 外部 CMS: 管理 UI は充実するが、今回の VS Code と Git を中心とする編集方法にサービス運用が増える。
- Markdown から型付きモジュールへ変換する: 編集をファイル単位で行え、実行環境とホットリロードを既存の Next.js に揃えられる。

## 影響とトレードオフ

- 通常の更新で TypeScript や JSX の編集は不要になる。
- 誤字や日付の逆転をファイル名付きで検出でき、下書きは生成された公開データに入らない。
- `order` と安定 ID は内容の管理項目として残す。活動は未指定なら日付順、制作物・技術は表示順とファイル名で並べる。
- 標準の開発・ビルド・型チェックコマンドを使う必要がある。Next CLI を直接実行すると変換や監視を経由しない。
- 原稿の管理は公開リポジトリ自体の公開範囲に従う。`draft` はサイトへの掲載設定であり、Git の公開範囲を変えない。
- フレームワークや本文形式を変える場合も、編集元と表示モデルの間で変換を差し替えられる。
